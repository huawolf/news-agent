# News Agent - Processing and Sync

> Part of the [system architecture](system-architecture.md). Section numbers are preserved for code cross-references.

## 7. Processing Pipeline

### 7.1 Master fetch cycle

Master and slaver share the fetch cadence (`schedule.fetch_interval_minutes`, default 60 minutes) and pipeline shape, differing only in source scope. Master explicitly skips `kind = feed`; it collects enabled RSS and the remaining built-in adapters.

```text
all enabled RSS
  -> Feed-page collection (master skips)
  -> allowed built-in adapters (GitHub Trending: master only; yield crawl: slaver/browser path only)
  -> freshness and quality gates
  -> GitHub Trending split: no pre-dedup, no signal-pool insert; refresh cache from scored top N (master only)
  -> URL / BM25 pre-deduplication
  -> batch scoring of non-duplicates
  -> URL / BM25 re-check before persistence
  -> persist with first_seen_at = write time
  -> master queues target-language translations
```

`first_seen_at` is generated by the writing instance and cannot reuse `published_at`; slaver sync depends on it.

### 7.2 Scoring contract

`prompts/score_batch.md` defines the investment-researcher role. The goal is to surface actionable investment signals and material industry progress, not to write news summaries. Prompt text is English; output language is supplied through the dynamic output-language instruction. Examples must cover multiple sectors, including macro, commodities, and crypto, so the model does not learn a narrow AI-only preference.

`interest_score` has three tracks of equal importance and equal priority:

1. **Investment value:** material change to revenue, profit, cash flow, valuation, supply-demand, regulation, or competitive position.
2. **Startup value:** unmet demand, new business model, user or revenue growth, unit economics, financing, M&A, or competitive structure.
3. **Material progress in the relevant sector:** a substantive change that shifts expectations, not mere theme membership. Each enabled sector uses the same standard.

An industry, financing, regulatory, supply-demand, or competitive change can score 80 or higher even without a specific ticker or when direction must be `neutral`. The prompt explicitly forbids discarding an item only because it is not AI news or downgrading it only because its sector is niche.

Scoring output includes `assets`, `direction`, and `sectors` in addition to scores and display text.

Asset rules:

- `assets` is always English, uppercase, with no spaces, hyphens, `$` prefix, or exchange suffix. This does not change with output language.
- Stocks, ETFs, and crypto tokens use common tickers such as `NVDA`, `AAPL`, or `BTC`.
- Non-security assets use one standard English form such as `CRUDEOIL`, `GOLD`, `DXY`, `US10Y`, or `BRENT`.
- Indexes and themes use forms such as `NASDAQ100`, `SP500`, `PHLXSEMI`, or `AICHAIP`.
- At most five assets are allowed per signal. If no standard form is known, omit the asset rather than emitting a placeholder or a Chinese name.
- The application removes surrounding whitespace and `$`, removes internal whitespace, uppercases, deduplicates, and discards non-ASCII and overlong values. Discarding Chinese is intentional: accepting it would reintroduce a second spelling of the same entity.
- There is no ticker-existence validation because there is no asset master table. The hard spelling rule plus deterministic normalization is the current contract.

Direction:

- `direction` is one of `bullish`, `bearish`, or `neutral`; invalid values become `neutral`.
- The judgment is based on the most affected asset. Bullish means a reasonable expectation of a 2% or greater rise; bearish means a 2% or greater fall. Insufficient magnitude, conflicting evidence, or no asset means neutral.
- Company product, beta, or partnership news may link a ticker, but a link is not automatically bullish. Without verifiable adoption, revenue, order, or profit impact, use `neutral`.

Sector and event rules:

- Return only exact enabled sector names. Filter unknown names before persistence.
- One signal carries one event and one core subject. Daily briefs, weekly roundups, market recaps, rankings, and multi-event compilations set `is_aggregate: true`.
- Headline-only or otherwise unanalyzable input sets `is_low_content: true`.
- Content with no actionable increment sets `is_low_value: true`.
- A discard flag produces empty text, zero scores, and no assets, sectors, or keywords. At most one flag is true.

Batch budgeting uses the actual rendered prompt. `llm.max_prompt_chars` applies to the final prompt, including the `indent=2` entries JSON, the full template, and the recent high-score title block. The implementation renders an empty prompt once to obtain the base length and adds entries by their marginal rendered length. The scoring context includes the most recent 100 visible titles with `final_score > 80`; the model omits duplicates from `items`, and omitted entries count as duplicates after scoring.

### 7.3 Final-score ranking

`final_score` starts from the LLM `score` and applies configured ranking adjustments, clamped to 0-100:

```text
score
+ interest keyword bonus
+ source weight
- avoid-keyword penalty
+ 24-hour recency bonus
-> clamp to 0..100
```

`watchlist_bonus` exists in the ranking helper, but current local collection and master report paths do not pass a watchlist, so it does not affect insertion today. The portal filters and sorts by `final_score`.

### 7.4 Deduplication

Deduplication is a reusable component shared by local collection and master report ingestion. Local collection pre-deduplicates before scoring and re-checks before persistence. Master report ingestion translates when necessary, deduplicates, scores, then re-checks.

**Level 1: URL, only when present.** Normalize the URL by removing `utm_*`, `spm`, `from`, `ref`, fragments, and trailing slashes, then check `signal.url` and `signal.source_urls`. A match is a duplicate and is discarded without consuming energy. URL-less signals skip this level.

**Level 2: BM25.** Recall candidates from `title_search` and `content_search`, rank them with application-level BM25, and take the top 10.

- No candidate or a top score below the low threshold: unique, continue.
- Top score at or above the high threshold: duplicate, archive only.
- Gray-band score: unique, continue.

Default thresholds are `bm25_high_threshold = 100` and `bm25_low_threshold = 40`. They are calibrated for the dedup query construction below; changing the query token cap requires recalibrating both thresholds.

URL duplicates and BM25 high-threshold duplicates are written to `dedup_duplicate` and application logs. Gray-band candidates are not recorded. There is no manual review queue and no pending adjudication state.

BM25 recall, corpus statistics, and FTS/trigram indexes cover visible rows only. Hidden rows do not influence similarity thresholds. URL lookup intentionally stays full-table so a hidden row with the same URL still blocks re-scoring.

### 7.5 Tokenization and BM25

Chinese tokenization uses `jieba` exact mode as a hard dependency. It handles mixed Chinese and English text: Chinese is split into words, while English and digits stay intact and are lowercased. Stopwords are filtered in the application.

Tokenization happens before storage. `title_search`, `summary_search`, `keywords_search`, and `content_search` are ordinary columns. Query paths do not invoke jieba at read time.

Additional rules:

- Asset tickers are appended to `title_search` in uppercase so asset search is not lost to lowercasing.
- A configurable user dictionary can add asset aliases, product names, and sector terms.
- Dedup queries strip HTML and URLs, tokenize with the same jieba path, remove stopwords, punctuation, digits, and single letters, keep English tokens of at least two letters and Chinese tokens containing CJK characters, deduplicate, and take the first `dedup.max_query_tokens` tokens (default 10).
- User search uses the same tokenizer, takes the first five tokens, and applies token AND.

Scoring formula:

```text
score = BM25(title_search, k1_title, b_title) * TITLE_WEIGHT
      + BM25(content_search, k1_content, b_content)
```

Defaults are `TITLE_WEIGHT = 3.0`, `k1 = 1.5`, and `b = 0.75`. PostgreSQL uses `pg_trgm` GIN plus `ILIKE` for recall; SQLite uses FTS5. Both send candidates to the same application-level scorer in `src/dedup/bm25.py`. BM25 searches only the most recent `dedup.window_hours` (default 72 hours) and applies a same-source bonus (`dedup.same_source_bonus`, default 2.0).

### 7.6 Push structure

A digest has three sections:

| Section | Default limit | Selection |
|---|---|---|
| Hot | `delivery.push_limits.hot`, 10 | Signals from the last 24 hours sorted by `final_score`; one highest-scoring signal per asset; topic quota applies. |
| Watchlist | `delivery.push_limits.watchlist`, 10 | Signals whose `assets` match the watched list and whose assets were not consumed by Hot; one per asset; shared topic quota. |
| GitHub | `delivery.push_limits.github`, 3 | Latest `github_cache` history after the GitHub push window; see 7.7. |

The first two limits are editable from 0 to 100; 0 disables that section. `delivery.push_limits.max_per_topic` (default 3) is shared by both signal sections. The topic key is `sectors[0]`, falling back to `source_name`. Under a tight quota, send fewer items rather than filling with low-score content.

`delivery.push_limits.min_score` defaults to 80 and is applied as `final_score > min_score`; exactly 80 does not qualify. Digest candidates are sorted by `final_score`, not arrival order. The portal's default batch-first ordering must not be reused for digests.

Four filters apply in order:

1. **Global asset deduplication:** an asset appears at most once across the whole digest, taking the highest score. Hot selects first. A multi-asset signal is rejected if it intersects any already-selected signal's assets.
2. **Previously pushed suppression:** a signal already present in `signal_push` is not pushed again. The window is unlimited; pushed once means read once.
3. **Cross-section exclusion:** Watchlist cannot reuse a Hot signal or an asset consumed by Hot. Both sections share one asset ledger.
4. **Topic quota:** at most `max_per_topic` signals with the same topic key across the two signal sections.

The two signal sections share one candidate pool sorted by `final_score`. Event-level duplicates that URL or BM25 cannot detect are handled by the LLM before persistence; the push layer does not build heuristic event keys.

GitHub is read from `github_cache`, which master writes and slaver pulls. If the cache is empty, fall back to GitHub signals from the last 24 hours, still subject to the push window. Only a successfully sent digest records its signal and repository pushes.

Push is triggered independently by `delivery.schedules` cron entries. It reads the local database only and never triggers fetch, pull, or report. Schedules may contain any number of weekday and `HH:MM` rows using APScheduler-compatible weekday names. The sample has every day at 09:00 and 17:00; an empty list disables scheduled push.

Each locale has its own digest, persisted under `latest_digest:<locale>`. Section titles and platform messages are localized. The main locale also writes the legacy `latest_digest` key. A schedule entry may carry `locale`; otherwise it uses the main locale, and one send never mixes languages.

### 7.7 GitHub Trending exception

GitHub Trending does not enter the two-level signal deduplication path and is not written to `signal`. After the quality gate, full trending candidates with README support go through the same `score_batch` call. The scorer rewrites the project name in the output language (at most 20 characters) and writes a 3-5 sentence summary. The top N by LLM score refresh `github_cache`; N comes from `fetch_source.params.max_items` (default 3). The payload carries `score`, `summary` (main-language LLM summary with raw description fallback), and `name`. On scoring failure or empty output, fall back to the original trending order without these fields.

Each refresh merges into a rolling seven-day history (`GITHUB_HISTORY_DAYS`). Each entry carries the earliest `first_seen_at` for that repository while other fields refresh from the latest score. Expired entries are pruned, so the portal can group GitHub Trending by day like other signals.

Repository push memory is separate from signal memory because repo text and news text are not comparable under one BM25 history. `github_push` records only repositories actually sent in a digest. Digest construction filters repositories pushed within `delivery.push_limits.github_window_days` (default 30 days) and then takes the top N. After the window, a repo that trends again may be pushed again.

GitHub display text is localized through `github_translation`, keyed by `(url, locale)`. The target locales follow the same rule as signals: every enabled locale except the main locale. The queue prefers the scorer's summary and falls back to the raw description. The translation worker fills `name` and `description`; `full_name` remains untranslated. The trending endpoint overlays completed rows and keeps cached text for pending or failed rows.

## 8. Slaver Cadence, Sync, and Conditional Fetching

### 8.1 Schedules

Fetch, push, and conditional translation work all run on the existing APScheduler instance.

| Trigger | Default | Action |
|---|---|---|
| Fetch | `schedule.fetch_interval_minutes`, 60 | Pull, collect, deduplicate, score, persist, report. |
| Push | `delivery.schedules` cron; sample at 09:00 and 17:00 daily | Read the local database and deliver. Never collects or reports. |
| Translation | `translation.interval_minutes`, 10 | Master only, and only when `content_languages` contains a locale other than the main locale. Retries pending and failed translations. |

Manual fetch is a console API action, not a scheduled job. Saving fetch or delivery settings rebuilds the affected jobs immediately.

### 8.2 Fixed fetch-cycle order

The order is pull, collect, then report. It must not be rearranged, because local deduplication needs the master pool before deciding which local items are unique.

```text
1.  Pull shared signals and late translations from master (two independent cursors and pages)
2.  Pull the master source catalogue (`/api/server/sources`)
3.  Collect RSS with conditional requests; skip feeds present in the master catalogue
4.  Collect Feed pages (slaver only; sequential through BrowserWorker)
5.  Collect other built-in adapters; GitHub Trending is not collected by slaver
6.  Apply 24-hour freshness and quality gates
7.  Run URL / BM25 pre-deduplication
8.  Reserve the reporter's daily scoring quota; drop over-limit candidates
9.  Batch-score candidates, then re-check URL / BM25
10. Persist visible and hidden rows locally
11. Report this cycle's visible new signals with `score >= 60` through MCP in batches
12. Pull and update the GitHub Trending cache
```

Steps 1-2, 11, and 12 belong to a connected slaver. A standalone slaver (`server_url` empty) starts with collection at step 3, keeps all results locally, and does not make master or manai-pic calls.

The source catalogue is used only to identify overlap, never as a collection list. Sources already present in the master catalogue are skipped to avoid duplicate work. A catalogue failure degrades to collecting all local sources; URL and BM25 deduplication plus master-side deduplication provide the fallback. A source directory failure does not abort collection.

**Known ordering gap:** the current orchestrator still requests the source catalogue after a failed shared-pool pull. The documented target is to skip that request when master is unreachable. Directory failure alone already falls back to collecting all local sources.

Feed pages are collected only by slaver. Each Feed fetch receives `since_time = max(previous successful fetch start, current 24-hour window start)`; the first fetch uses the window start. Empty successful results advance the cursor; failures do not. Using the start time prevents items published during a fetch from being skipped. BrowserWorker uses a dedicated session and per-site domain lock. Daemon, plugin, WAF, DOM parsing, and empty-result states are logged; source success and failure timestamps are updated for diagnosis.

Step 12 is a pull, not a refresh: slaver never collects GitHub Trending. A cache miss leaves the section empty and logs at INFO without blocking earlier collection.

Reporting follows fetch rather than push because report is data synchronization. Each cycle collects only its own new visible `slaver` signals and calls `report_signals` in batches of at most `report.batch_size` (default 200). Hidden local rows are not reported. Transport and tool errors retry; authentication failures do not. Failed signals are not queued for a later cycle. MCP sessions are reused across cycles; do not reinitialize for every batch.

### 8.3 Sync windows and cursors

The slaver cursor is the singleton `sync_state` row with `scope = pull`. Each pull uses:

```text
[max(last_pulled_at, now - max_lookback_hours), now]
```

The default `sync.max_lookback_hours` is 24. Pagination is ascending by `first_seen_at` until exhausted.

```text
first run or no cursor       -> last 24 hours
normal run                   -> from last_pulled_at to now
offline more than 24 hours   -> clamp start to now - 24 hours; older gaps are abandoned
master unreachable           -> leave last_pulled_at unchanged; resume from it later, clamped if needed
```

The window uses `first_seen_at`, not `published_at`. A late-collected article may have an older publication time; ordering by `published_at` would miss it, while `first_seen_at` is monotonic in the master's ingestion order.

The server also clamps an over-old valid ISO cursor to `now - 24 hours` instead of returning 400. Only an invalid time format returns 400.

The cursor advances only after both signal and translation streams have completed every page. A failure leaves it unchanged and retries the same segment next cycle. Already stored rows are protected by deduplication.

Late translations are a separate stream. The response carries `items` for new signals (cursor `last_pulled_at`, ordered by `first_seen_at`) and `translations` for completed locale rows whose `updated_at` falls in the window (cursor `last_translation_pulled_at`, ordered by `updated_at`). Each has its own page number and `has_more`. A slaver updates title, summary, keywords, and their search columns in place; it never changes `content` or `content_search`. When the requested locale is the main locale, the translation stream is empty.

`last_translation_pulled_at` follows the same `max(cursor, now - 24h)` floor. `peer_sync_state` records master-side pull observations. The model exposes a peer `last_failure_at`, but the current server has no write path for peer failures, so it does not reflect failures today.

Pulled items preserve `origin`, `reporter`, and `reporter_name` exactly. Slaver must not rewrite a shared signal as its own user id and must not flatten the reporter to `0`; otherwise local provenance and reproduction diverge from master.

If master is unreachable, collection and local storage continue, but there is no persistent outbound queue. Signals whose report attempt failed stay local for local delivery and are not backfilled automatically. A slaver that is behind by more than 24 hours permanently abandons the older gap and logs INFO rather than writing a discard record.

### 8.4 RSS conditional requests and Feed cursors

RSS stores ETag and `Last-Modified` per source and sends them on the next request:

```http
GET /feed.xml HTTP/1.1
If-None-Match: "s-4821-a3f9c2"
If-Modified-Since: Wed, 01 Oct 2026 09:00:00 GMT
```

| Response | Handling |
|---|---|
| `304 Not Modified` | Skip the source for this cycle: no parse, no insert, no XML body stored. |
| `200 OK` | Parse normally and update the stored fingerprint. |
| No fingerprint | Degrade to a full fetch. |
| `429` or `5xx` | Keep the old fingerprint, set `last_error_at`, and retry next cycle. |

`304` means the body did not change. Storing the XML would add a copy that is guaranteed to be discarded; parsed entries already live in `signal`.

Conditional request logic must cover both HTTP paths: standard RSS through `aiohttp` and Nitter/xcancel through `requests` with lower concurrency and extra sleeps. Changing only one path permanently degrades the other to full fetches.

Feed-page sources do not use ETag. They reuse `last_fetched_at` as the start time of the last successful fetch and apply the 24-hour floor described above.

There is no per-source frequency scheduling and no active fingerprint invalidation. `304` skip and `200` update are sufficient.
